# Hippocore DB — Data Model and Context Projection

## Product definition

Hippocore DB is a local-first database where stored information can become
native context for AI systems.

It must be useful as a database first: users and applications should be able to
insert, manage, inspect, delete, and retrieve information. Its AI-native
difference is that each supported data shape can also be projected into
searchable, citeable, auditable context for SDKs, agents, and RAG applications.

## Core idea

```
stored data → context projection → indexed entry → recall/search/build_context
```

The database should not treat context as an external preprocessing artifact.
Context projection is a native responsibility of Hippocore DB.

## Current entities

| Entity | Status | Role |
|--------|--------|------|
| `Tenant` | implemented | Top-level isolation boundary. |
| `Collection` | implemented | Logical group of stored data within a tenant. |
| `Document` | implemented | Stored text managed as one object. |
| `Chunk` | implemented | Searchable slice of a document. |
| `Memory` | implemented | Atomic remembered fact/procedure/note/event. |
| `IndexedEntry` | implemented internally | In-memory searchable projection of one chunk or memory. |
| `WAL Entry` | implemented internally | Durable mutation record for recovery. |

## Planned entities

These are product concepts, not immediate implementation commitments.

| Entity | Role |
|--------|------|
| `File` | Original file object with path/name/media type/checksum/source metadata. |
| `Table` | Structured dataset namespace, similar to a lightweight table. |
| `Record` | Structured row/document, likely JSON-first in the early MVP. |
| `ContextItem` | Public context unit returned to SDKs/agents, independent of whether it came from a document, memory, record, or file. |
| `ContextTrace` | Future audit record tying question → retrieval → context → answer. |

## Context projection

Every data type that is made searchable should define a deterministic projection
into context:

- `kind`: document chunk, memory, record, file-derived chunk, etc.
- `text`: searchable text representation.
- `embedding`: generated by built-in embedder or supplied by caller.
- `metadata`: exact-match filters and domain tags.
- `source`: provenance for citation and inspection.
- `tenant` / `collection`: isolation and grouping.
- `timestamps` / `version`: current data lifecycle signals.
- future `confidence` / temporal validity fields.

Examples:

```txt
Memory
  text: "PostgreSQL uses TCP port 5432 by default."
  → one ContextItem / IndexedEntry

Document
  text: "Long troubleshooting guide..."
  → chunks → many ContextItems / IndexedEntries

Record
  table: "systems"
  json: {"name":"billing-db","engine":"postgresql","port":5432}
  → projected text: "systems record name billing-db engine postgresql port 5432"
```

## Structured data direction

Hippocore should support structured data without becoming SQL-first too early.

The first structured-data increment should be JSON-record oriented:

```rust
db.put_record("tenant", "systems", json!({
    "name": "billing-db",
    "engine": "postgresql",
    "port": 5432
}))
```

Expected behavior:

- Store the original JSON record durably.
- Preserve exact fields for filters/inspection.
- Create a text projection for retrieval.
- Return record-derived context with source/type information.

This keeps the path open for table-like management and later query languages
without prematurely implementing SQL.

## File ingestion direction

Files should become first-class stored objects before multimodal processing is
expanded.

Early scope:

- `.txt`, `.md`, `.json`, `.csv` ingestion.
- Store file metadata: path/name/media type/checksum/source.
- Project text-like files into documents/chunks or records.
- Keep binary/OCR/PDF/multimodal extraction for later phases.

## SDK context API direction

The public API should evolve from raw recall toward explicit context operations:

```rust
db.search_context(query)
db.build_context(query, max_tokens)
```

The output should be context-oriented, not only storage-oriented:

- ranked context items;
- citations/source;
- scores and reasons;
- metadata;
- missing-context signals;
- future audit trace id.

## Non-goals for the next increments

- Full SQL engine.
- PostgreSQL wire protocol.
- HNSW.
- Server mode as a prerequisite for local embedded use.
- Multimodal extraction beyond simple text-like files.

The near-term goal is to make the data model explicit and extensible while
preserving the local-first embedded core.
